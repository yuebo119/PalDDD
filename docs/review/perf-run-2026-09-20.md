## 二、关键归因

1. **EF GetPending −31% 属实**：谓词下推（单语句替代整表翻页）的直接收益，与 fcb5ed3 实施一致。
2. **EF Lease −11%/分配 −41% 属实**：批量化消除 N 次 UPDATE 往返的往返与 EF 物化开销；剩余 11.19ms 的主体仍是基准方法体内耗尽型重灌（已裁决归 B1/上游）。
3. **Dapper Lease +54% 判为噪声+环境漂移**：本轮 Dapper 侧变更仅注释勘正与分类器收口（均不触 Lease SQL 热路径——git diff 逐行核对）；Error 530μs（11%）+ StdDev 1.56ms 表明 ShortRun 下该基准自身波动带即 ±30%+。基线自订纪律「偏离 >10% 需 medium 复测」——复测值为 2.945ms（与基线 2.919ms 几乎一致），**确认本轮实测无回归，ShortRun 数字不可作裁决依据**。
4. **EF AddSingle/EventLog/Idempotency +24~48%**：本轮变更未触这些路径；同 run 内 Dapper 同基准全部下降——倾向为 EF 管道在当前机器状态的漂移 + InProcess 多模态警告（BDN 自报 multimodal）。medium 复测定性后再议。

## 三、优化方案（数据驱动）

### P1（做，S 级）：FanOut 车道基准锚
骨架重构刚完成（行为有表征测试、性能无锚）。加 `Saga_ProcessEvent_Normal/FanOut` 两项基准（S 级），给未来 v3.0 子项粒度改造一个 before 锚。**这是唯一新基准建议**。

### P2（做，S 级）：medium 报告归档纪律
本轮实证 artifacts 覆盖问题（medium 跑后 github.md 只剩 Lease 行）。处置：`--persist-medium` 输出改写独立文件名（如 `*-medium-report-github.md`），medium 数字追加进 `docs/performance.md` 时带日期。防「裁决数字无处查」复发。

### P3（做，M 级）：EF Inbox 抢占 ExecuteUpdate 化的量化验证
F1 修复（3586125）改写了抢占路径形态，当前只有功能回归测试。若 Inbox 吞吐成为用户场景，加 `Inbox_TryStart_Compete` 基准验证 ExecuteUpdate 无回退（此前 SaveChanges+并发异常路径在冲突时有重抛成本）。**触发条件：有用户场景数据再做**。

### 不做清单（数据支持的取舍）
- **EF AddSingle +28% 追查**：未触路径 + 环境漂移嫌疑 + 单点 ShortRun 数字——medium 复测若确认上升再立案；本轮不动。
- **B1 Pooling**：已实测 4.4% 收益，维持 v3.0 捆绑裁决（4d 决策）。
- **PalORM Lease −46% 的「反哺」**：PalORM 本轮大改善属 inherit（架构未变），无需动作。
- **GetPending 继续压**：EF 668μs 已接近 Dapper 651μs——三栈同量级目标达成，收手。

## 四、结论

三栈热路径「同一量级」的核心判断**维持成立**（GetPending 三栈 359-668μs；Lease medium 2.9/3.4/11.2ms）。本周两项性能实施（Lease 批量化 + GetPending 下推）经独立复测验证有效且无回归。优化重心应从持久化栈转向 ①Saga 车道锚（唯一空白）②文档/流程类小改（medium 归档纪律）。
