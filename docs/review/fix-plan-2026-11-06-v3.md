## 1. v3 的编制纪律（为什么这次不再返工）

v2 的失败模式是**「方案修法描述与代码结构不精确」连续复发**：B2 挂起前提、B2 降级形态、B4 局部任务可见性、S1 观测点、S6 affected 概念，共 5 处。v3 每条修法强制三件套：

2. **编译级探针**：隔离 file-based app（`/tmp/v3probe/ProbeN.cs`）或目标项目构建，三查「编译错误 / 警告 / 退出码」，结论入档。禁止只看 warning 计数（v1 S1994 探针教训）。
3. **公共 API 影响判定**：触及 `public` 类型/接口即显式标注快照 + CHANGELOG 同提交同步（G23），不承诺「零公共 API 变化」而实际改接口集合。

### 2.1 B2：Rabbit 批量 pre-ack → `IMessageAck` DIM 移交标记

**目标代码结构摘录**：

`src/PalDDD.Messaging/MessageAck.cs:29-44` — 公共接口只有两个方法，无扩展点：
```csharp
public interface IMessageAck
{
    ValueTask AcknowledgeAsync(CancellationToken ct = default);
    ValueTask RejectAsync(bool requeue, CancellationToken ct = default);
}
```

`src/PalDDD.Messaging.RabbitMQ/RabbitMqBroker.cs:475-479, 519-523` — broker 每次交付 new 私有确认器，handler 返回后按 `IsSettled` 兜底 ACK：
```csharp
var ack = new RabbitMqMessageAck(this, consumerChannel, ea.DeliveryTag, queueName);
...
await handler(message, consumeContext, ack, deliveryCts.Token).ConfigureAwait(false);
if (!ack.IsSettled)
    await TryAckSafeAsync(consumerChannel, ea.DeliveryTag, queueName).ConfigureAwait(false);
```

`src/PalDDD.Messaging.RabbitMQ/RabbitMqBroker.cs:701-739` — 私有确认器持 `channel` 引用，`TryClaim` 原子占位：
```csharp
private sealed class RabbitMqMessageAck(...) : IMessageAck
{
    private int _settled;
    public bool IsSettled => Volatile.Read(ref _settled) != 0;
    public bool TryClaim() => Interlocked.Exchange(ref _settled, 1) == 0;
    public async ValueTask AcknowledgeAsync(CancellationToken ct = default) { ... broker.TryAckSafeAsync(channel, ...); }
    public async ValueTask RejectAsync(bool requeue, CancellationToken ct = default) { ... broker.TryNackSafeAsync(channel, ...); }
}
```

`src/PalDDD.Messaging/MessageBatchPump.cs:92-98` — 泵把 broker 的 ack 原样入队；`:172-181` 批次收尾用 `MessageBatchAck` 逐条委派：
```csharp

...
if (!batchAck.IsSettled) await batchAck.AcknowledgeAsync(ct).ConfigureAwait(false);
```

`src/PalDDD.Messaging/PalDDD.Messaging.csproj:17` — IVT 只开 DI/Tests/Kafka，**不含 RabbitMQ**；`src/PalDDD.Messaging.RabbitMQ/PalDDD.Messaging.RabbitMQ.csproj:24` 只开 Messaging.Integration.Tests。

**v3 唯一解（不动泵聚合逻辑、不改 broker 传输结构、零挂起）**：

1. 给 `IMessageAck` 加两个**默认接口成员**（DIM）：`bool IsSettlementDeferred => false;` 与 `void DeferSettlement() { }`。DIM 不破坏现有实现者（NoOpMessageAck / MessageBatchAck / KafkaMessageAck / RabbitMqMessageAck 均无需改动即可编译）。
2. `RabbitMqMessageAck` 覆写两成员：私有 `int _deferred`；`DeferSettlement()` 置位；`IsSettlementDeferred` 读位。
3. 泵 `EnqueueAsync` 前经 `IMessageAck` 接口调 `ack.DeferSettlement()`（泵在 Messaging 程序集，DIM 是 public 接口成员，无需 IVT）。**Kafka 的确认器不覆写 DIM → 默认 false → Kafka 兜底行为零变化，吞吐零影响**（批 0 探针的吞吐退化问题自然消解）。
4. Rabbit broker 三处兜底（`:522` 成功 ACK、`:543`/`:555`/`:564` 失败 Nack）与 null 分支（`:530`）统一把判据从 `!ack.IsSettled` 改为 `!ack.IsSettlementDeferred`；该标记在 handler 返回时已为 true（泵入队时打的），故兜底整体跳过。
5. 批次收尾 `MessageBatchAck` 逐条调 `AcknowledgeAsync/RejectAsync`，真确认器持 channel 引用完成结算（不需要 TCS 挂起，不需要 broker 回调存活）。

**公共 API 影响**：`IMessageAck` 新增 2 个 DIM 成员 → `core-packages-public-api.txt` 快照 `interface PalDDD.Messaging.IMessageAck` 段（当前 994-996 行）增 2 行：`property System.Boolean IsSettlementDeferred` + `method System.Void DeferSettlement()`（快照生成器 `PublicApiSnapshotTests.cs:38-39,55-59` 用 `GetProperties`/`GetMethods(DeclaredOnly, !IsSpecialName)` 反射 dump，DIM 属性与非 special-name 方法均会列出，已核）。同提交改 CHANGELOG `[Unreleased]`（G23 逐提交同集耦合）。这是**加法式接口扩展**，不破坏任何现有实现者（探针 2 已证），不是 v2 承诺的「零公共 API 变化」——v3 显式登记该偏差。

**编译级探针（`Probe2.cs` / `Probe8.cs`，本轮实跑）**：

| 探针 | 结论 | 三查 |
|------|------|------|

### 2.2 B4：超时 abandoned scope → per-request 任务袋 + Dispatcher 等收尾

**目标代码结构摘录**：

`src/PalDDD.CQRS/TimeoutBehavior.cs:70-84` — `running` 是局部变量，超时后 `ObserveFault` 只观察异常：
```csharp
var running = task.AsTask();
try { return await running.WaitAsync(_timeout, ct).ConfigureAwait(false); }
catch (TimeoutException) { ObserveFault(running); throw CreateTimeoutException(); }
```

`src/PalDDD.CQRS/Dispatcher.cs:313-314` — HTTP 路径直接复用 `RequestServices`，不自建 scope：
```csharp
if (requestServices is not null)
    return await entry.Executor(requestServices, request, ct).ConfigureAwait(false);
```

`src/PalDDD.Hosting.AspNetCore/AspNetCore/EndpointExtensions.cs:57,97,184` — 三个端点传 `context.RequestServices`；`ExceptionMiddleware.cs:106-122` 把 `TimeoutException` 映射 504。

**v3 唯一解**：

1. `PalDDD.CQRS` 内新增 `internal static class PipelineBackgroundTasks`，持 `static readonly AsyncLocal<ConcurrentBag<Task>?> _current`。
2. `TimeoutBehavior` 两处 `WaitWithTimeoutAsync` 在 `catch (TimeoutException)` 里：`PipelineBackgroundTasks.Register(running)`（把后台任务登记进**当前请求**的袋）。
3. `Dispatcher.ExecutePipelineAsync` 在 `requestServices is not null` 分支改为：先 `PipelineBackgroundTasks.CreateScope()`（**每请求显式 `_bag.Value = new()`**，不是 `??=`）→ await `entry.Executor(...)` → 无论成功/超时/OCE，在返回前 `await PipelineBackgroundTasks.DrainAsync()`（等袋内全部任务收尾，带 `ShutdownTimeout` 上界防不响应取消的 handler 永久阻塞）→ 再返回。scope 由 ASP.NET 在端点方法返回后释放，此时后台任务已收尾，ODE 消失。
4. `ObserveFault` 保留（观察异常），但补 `_logger.Warning` 记录 abandoned 任务故障（零日志缺陷闭合）；`TimeoutBehavior` 不依赖日志门面的具体类型，用现有 `IPalLogger` 注入或经 `PipelineBackgroundTasks` 的可选回调。
5. 双写风险（504 重试）**不在此修**：属业务幂等键设计，v3 只登记「CQRS 请求面无幂等键」为已知缺口，与 v2 §4 B4 同口径。

**关键约束（编译级探针实跑）**：

| 探针 | 结论 |
|------|------|
| `Probe3.cs` | `AsyncLocal<ConcurrentBag<Task>>` 跨 await 边界可见：内层登记 1 个任务，外层读到 `bag count=1` 并 `WhenAll` 等收尾成功 |
| `Probe4.cs` | 每请求显式 `_bag.Value = new()` → 三个并发请求各自 `bag count=1`，互不污染 |
| `Probe5.cs` | 用 `??=` 沿用共享袋 → 三个请求共享 `bag count=3`（**污染实证**）→ v3 写死必须显式新建 |

**公共 API 影响**：新增 `internal` 类型 + 改 `Dispatcher`（public sealed）内部实现，零公共签名变化。

**锁定测试**：504 后 abandoned handler 完成前 RequestServices 不释放（scope 内 scoped 依赖可解析）；abandoned handler 抛异常时 Warning 可观测；双写反事实用例（幂等键缺失登记）；超时车道 504 时序不变（WaitAsync 仍在 _timeout 后抛）。变异：删 `DrainAsync` → scope 提前释放用例转红。

**v3 唯一解（两栈分形态，不套用 Outbox 样板）**：

- **Inbox（关系型）**：`MarkProcessedAsync`/`MarkFailedAsync` 在变异前保存 `(Status, ProcessedAt, LastError)` 快照；`SaveTerminalStateAsync` 改为返回 `bool`（`affected > 0`），调用方在 `false` 时把三字段回退到快照（DB 仍为 Processing，入参不再持假 Completed）。非关系型路径在 `DbUpdateConcurrencyException` 分支同样回退。
- **Inbox（非关系型）**：同上，异常分支回退。
- **Idempotency**：并发冲突时**不能简单回退到 Processing**（DB 已被另一节点写成 Completed/Failed），且**不能把 DB 真值覆盖回入参**——`src/PalDDD.Idempotency/IdempotencyRecord.cs:66,80` 的 `Status`/`Revision` 是 `private set`；`:56` 的 `internal RestoreTerminalState(...)` 只回填 `ResponsePayload`/`Error`；`src/PalDDD.Idempotency/PalDDD.Idempotency.csproj:16-17` 的 IVT 只开 `PalDDD.PalORM` / `PalDDD.Dapper`，**不含 `PalDDD.Idempotency.EFCore`**（后者 csproj:13 只有 ProjectReference）。因此 EF 栈**无法**在程序集内复原入参终态。
  v3 收敛形态：① 在 `PalDDD.Idempotency` 给 `IdempotencyRecord` 增一个 `internal void RestoreFromStore(IdempotencyRecordStatus status, long revision, ReadOnlyMemory<byte>? payload, string? error, DateTimeOffset updatedAt)`（一次性把五字段按 DB 真值复原，**不递增** Revision，语义对齐既有 `RestoreTerminalState` 的「回放非状态转移」声明）；② 给 `Idempotency.csproj` 增 `<InternalsVisibleTo Include="PalDDD.Idempotency.EFCore" />`；③ `SaveTerminalStateAsync` 的 `DbUpdateConcurrencyException` 分支 `AsNoTracking` 重读该 key 的 DB 行，调 `RestoreFromStore` 覆盖回入参。若重读不到行则记 Warning 并保持 Detach。
  这是**新增 internal 成员 + 新增 IVT**（不进公共 API 快照，不改变任何 public 签名），但跨 `PalDDD.Idempotency` / `PalDDD.Idempotency.EFCore` 两程序集，需在 v3 批次里占独立提交。
- 三处 `Mark*` 公共签名不变（仍 `ValueTask`），`SaveTerminalStateAsync` 是 `private`，零公共 API 快照变化。

**编译级探针（`Probe6.cs`）**：`accepted: Status=Processed ProcessedAt=1970-01-01`；`rejected: Status=Processing ProcessedAt= LastError=old-error`（期望值全中）→ 快照回退形态编译成立、语义正确。0 错误 0 警告 exit 0。

**覆盖率门禁专项（本轮实证，写入 v3 纪律）**：任何新增测试项目辅助类前必须核对目标测试项目的插桩分母。`CI run 42244424678` 实证：在 `DependencyInjection.Tests`（窄分母）新增 Saga 派生类把 `PalDDD.Transactions` 全程序集计入分母 → 24.39%→15.54%（降幅 9.05pp > 5pp）。修法是把测试移到分母本就含该程序集的项目（`Transactions.Tests`），不改基线、不删断言；`ALLOW_TEST_ONLY_CHANGE=1` 豁免须在提交信息写明正当理由。v3 批 A~H 新增测试均须按此口径预核落点。

## 7. 风险与回退

- **批 A（B2 DIM）** 是唯一改公共接口的 P1 修复：DIM 不破坏现有实现者（Probe2/8 实证），但接口集合变化会进快照；若 CI 快照门禁红，原因是快照未同提交更新，不是修法问题。
- **批 B（B4 AsyncLocal）** 的硬约束：任务袋必须每请求 `_bag.Value = new()`（Probe4），禁止 `??=` 沿用（Probe5 实证三请求共享污染）；`DrainAsync` 须带 `ShutdownTimeout` 上界，防不响应取消的 handler 让 504 无限期阻塞。
- **批 C（S6）** 跨 `PalDDD.Idempotency` / `PalDDD.Idempotency.EFCore` 两程序集，新增 IVT 后须跑 AOT 样本；`RestoreFromStore` 须明确「不递增 Revision」（对齐既有 `RestoreTerminalState` 的回放语义声明）。
- **批 G** 是唯一需要新 ADR 的批次（ADR-038），且 5 项 API 中 3 项改现有签名（A2/A3 主构造器、A1 接口成员）→ 需 SemVer 评估；v3 只排顺序，实施轮按 `docs/release.md` 判据定版本。
- **批 F** 的 Stryker 每周 schedule 不进 push 主路径，其「拒绝过吗」证据只由 gate-audit 式变异探针承载，不得用「千级基数」替代。
- 每批提交前 `dotnet run scripts/gate.cs`（G22/G23/G24）+ `dotnet run scripts/gate-audit.cs` + pre-commit 全钩；公共计数器/API 变更同提交同步 count-audit 16 项扫描面 + 快照 + CHANGELOG。
- **推送状态**：本方案文档提交（`docs/review/fix-plan-2026-11-06-v3.md`）与 `f3e0d0a`（coverage 回归修复）均**未推送**，需用户单独显式授权 `git push` 后才上 CI 复核 coverage 转绿。
