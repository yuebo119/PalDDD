## 2. 三条致命项的 v2 修法（到代码形态）

### 2.1 B3：Kafka 毒消息冻结水印 → ack 提升 + finally 统一结算

`KafkaBroker.cs:752-811` 重构 `HandleMessageAsync`：

1. `KafkaMessageAck? ack = null;` 提升到 `try` 外（:754 前）。
2. EOF（:760）/ tombstone（:764）分支直接 `return`，不创建 ack（这两类本就不进 offset 跟踪 :532-533，无需结算）。
3. 非 EOF / 非 tombstone 消息：在反序列化**之前**构造 ack（即把 :780-784 上移），确保 null 分支（:787-791）也有 ack 可结算。
4. 新增 `finally`：`if (manualStore && ack is { IsSettled: false } && !tokenSnapshot.IsCancellationRequested) await ack.RejectAsync(requeue: false, CancellationToken.None);`
   - `manualStore` 门控：自动存储模式不结算（`RejectAsync(false)` 本就早退，但 `TryClaim` 会置 `_settled`，门控后零状态变化）。
   - `!ack.IsSettled`：handler 已显式结算（Ack/Reject/Seek）时不覆盖其决定。
   - `!tokenSnapshot.IsCancellationRequested`：关停窗口不结算——`EnqueueAsync`（:926-932）的 `WaitAsync(ct)` 在已取消 token 上立即抛 OCE，且消费线程 finally（:560-563）已放弃队列命令，补结算必然异常逃逸出 catch。
   - `CancellationToken.None`：finally 结算不受外部取消打断；消费线程 `Consume(100ms)` 每轮排空命令（:499），100ms 内落地。
5. **删掉**:894 `KafkaMessageAck.IsSettled`？**不删**——finally 需要它做判定。S1144 改由 `#pragma warning disable S1144` 定点抑制 + 注释「由 HandleMessageAsync finally 判定」（v1「删死属性」与本修法冲突，红队第 10 条成立）。

行为论证：自动模式零变化；手动模式 handler 异常/反序列化 null → RejectSkip → `OffsetTracker.Ack` 前缀推进（:981-998）解冻；关停 OCE 走 at-least-once 重启重放（既有语义 :560-563）；EOF/tombstone 不进跟踪不结算。锁定测试：`EnableAutoOffsetStore=false` + handler 抛异常 + 后续消息 offset 推进（现有 BrokerIntegrationTests.cs:580-623 毒消息用例走二参旧重载、默认配置，断言不到 offset，必须新增）。

### 2.2 B2：Rabbit 批量 pre-ack → `DeferredMessageAck` 单点识别

v1「分层结算」散到三处（四参删兜底 / 三参包装层补 ACK / 接口文档改写），且有三处实证问题：三参 `:379` 的 lambda 用 `_` 丢弃 ack，包装层需捕获 ack 才能调 `AcknowledgeAsync`（v1 未写）；`TryAckSafeAsync`（:670）/`TryNackSafeAsync`（:654）直接打 channel 不置 `_settled`，catch 安全网（:543/:555/:564）与泵 :194 的 `RejectAsync` 可二次 `BasicNackAsync` → `PRECONDITION_FAILED` 关 channel；`BasicQosAsync(0,10)` 下 10 条未结算即停推，远早于 v1 说的 30 分钟 consumer_timeout。

红队建议的 `deferSettlement` 标记不可行：`MessageBatchPump` 在 `PalDDD.Messaging` 程序集，其 `csproj:17` 的 IVT 只开给 DependencyInjection / Messaging.Tests / Messaging.Kafka，**未开 RabbitMQ**；`RabbitMqBroker : MessageBrokerBase`（:41）虽可加 `protected internal` 成员，但泵持 `IMessageBroker` 接口（:92-98），不能按具体类型调用。

**v2 唯一可行形态（不动公共接口、不改接口文档、零 IVT 变更）**：

1. `src/PalDDD.Messaging/MessageAck.cs` 新增 `internal sealed class DeferredMessageAck(IMessageAck inner) : IMessageAck`：`AcknowledgeAsync/RejectAsync` 只记结算意图（`int _settled` + `AckKind?`），不打 inner；暴露 `IsSettled` 与 `ApplyAsync(CancellationToken)`（把意图转给 inner，仅一次）。同程序集的 `MessageBatchPump` 可访问。
2. `MessageBatchPump.cs:92-98` 四参通路 lambda 改为：把 broker 传来的 `ack` 包成 `DeferredMessageAck` 再 `EnqueueAsync`；`PumpItem.Ack` 字段类型不变（`IMessageAck?`），`MessageBatchAck` 聚合逻辑（:172-181/:194-195）零改动。
3. 批次收尾后（泵 :205 `finally` 之前）对每个 deferred 调 `ApplyAsync`：把 `MessageBatchAck` 的聚合结算真正落到 broker 确认器。**关键**：`ApplyAsync` 必须在 broker 的 `ReceivedAsync` 回调仍存活时调用，否则 channel 已释放——因此泵在 `EnqueueAsync` 后让该条投递的 broker handler 等待一个 `TaskCompletionSource`，批次结算时 `TrySetResult` 释放。这意味着 `DeferredMessageAck` 需持有该 TCS；broker 侧 `await handler(...)` 因此挂到批次收尾，兜底 ACK（:520-523）自然落在结算之后且 `ack.IsSettled` 已真，跳过兜底；catch 安全网（:564-565）同理。
4. **不改 broker、不改接口文档**：四参直接用户旧语义零变化（未结算时兜底 ACK 仍在）；批量泵路径 broker 看到的是「handler 未返回 → 不兜底」，批次结算后 `ApplyAsync` 置 `_settled` 再让 handler 返回 → 兜底跳过；`RejectAsync(requeue:true)` 由 `ApplyAsync` 真转给 broker（v1 路径下静默无操作的缺陷闭合）。
5. 挂起形态的背压影响已排除：`RabbitMqBroker` 的 `ReceivedAsync` 是 per-delivery async 回调（:475），10 条 prefetch 上限内并发挂起属既有批量组批语义（泵通道容量 `maxBatchSize*4`，:79-85）；Kafka 侧四参通路不经过 `DeferredMessageAck`（其确认器走命令队列、非 channel ack），Kafka `slots`（:491/:664）不受影响——泵只对 `IMessageBroker.SubscribeAsync` 四参调用点包装，Kafka handler 的 `slots.Release()` 在 :666 由外层 finally 执行，与 handler 返回时长解耦（需核对 :655-670 段确认，作为批 2 的前置 10 分钟探针）。

**若第 5 点探针发现 Kafka slot 与 handler 返回耦合**（即挂起会卡并发），降级形态：不用 TCS 挂起，`DeferredMessageAck.ApplyAsync` 在批次收尾直接打 broker 确认器（broker 的 `ReceivedAsync` 已返回、channel 仍存活——`RabbitMqMessageAck` 持 channel 引用，:705），并把 broker 兜底改为识别 `DeferredMessageAck` 类型后跳过（需在 Rabbit 侧加 `internal` 类型判定，可用 `IMessageAck` 的标记接口 `IDeferredMessageAck` 定义在 Messaging 程序集，Rabbit 引用同一程序集无 IVT 问题）。两形态都零公共 API 变化。

锁定测试（缺一不可）：批次 handler 成功前 delivery 恒 unacked；批次收尾 AcknowledgeAsync 生效且零 Duplicate Warning；`RejectAsync(requeue:true)` 真重投；四参直接用户旧语义回归（成功 ACK / 异常 Nack(false)）；二次 Nack 竞态用例（关停 OCE 与泵弃置并发）。变异验证：删 `ApplyAsync` → 批量用例转红。
