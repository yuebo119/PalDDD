# 审计文档命名规范

> 范围：`docs/review/` 目录下的审计产出。
> 全局命名规范（项目/接口/类型/文档文件）见 `docs/conventions.md` §3。
> 核心规则：**`{type}-{date}[-v{n}].md`**。禁止主观形容词。

---

## 一、命名模式

| 文档类型 | 命名格式 | 示例 |
|----------|---------|------|
| **评审报告（现行主用）** | `review-{YYYY-MM-DD}[-full][-v{n}].md` | `review-2026-09-13-full-v5.md` |
| **评审报告（带主题）** | `review-{YYYY-MM-DD}-{topic}.md` | `review-2026-09-13-architecture.md` |
| **审计报告** | `audit-{YYYY-MM-DD}.md` | `audit-2026-06-30.md`（历史 corpus 用语） |
| **审计报告（同日多份）** | `audit-{YYYY-MM-DD}-v{n}.md` | `audit-2026-06-29-v2.md` |
| **审计补充** | `audit-supplement-{YYYY-MM-DD}.md` | `audit-supplement-2026-06-30.md` |
| **任务清单** | `action-items-{YYYY-MM-DD}.md` | `action-items-2026-06-30.md` |
| **任务清单（同日多份）** | `action-items-{YYYY-MM-DD}-v{n}.md` | `action-items-2026-06-29-v2.md` |
| **元审计报告** | `meta-audit-{YYYY-MM-DD}.md` | `meta-audit-2026-06-30.md` |
| **元审计报告（同日多份）** | `meta-audit-{YYYY-MM-DD}-v{n}.md` | `meta-audit-2026-06-30-v3.md` |
| **模板** | `{TYPE}_TEMPLATE.md` | `REVIEW_TEMPLATE.md` |
| **本规范** | `NAMING.md` | — |

**主题槽位（可选，2026-09-13 新增）**：当日同类型产出多份且主题不同时，
用 `{type}-{YYYY-MM-DD}-{topic}[-v{n}].md` 消歧，`topic` 为 kebab-case 主题词
（如 `audit-2026-09-13-rule-placement.md`）。此槽位为规范补充：原 `{type}-{date}`
模式无主题位，同日多主题产出只能靠 `v{n}` 区分，而版本号表达的是**顺序**不是主题
（规则 3），读者无法从文件名得知内容差异。

## 二、语法规则

### 规则 1：字段顺序

```
{type}-{date}[-v{version}].md
  ↑       ↑        ↑
  类型    日期     可选版本号
```

**错误示例**：
- `comprehensive-review-2026-06-28.md` — 类型词不在最前
- `serena-comprehensive-review.md` — 工具名混入类型
- `meta-audit-v2-2026-06-30.md` — 版本号在日期前
- `definitive-audit-2026-06-30.md` — 主观形容词禁止

### 规则 2：日期格式

- `YYYY-MM-DD`，四位年 + 两位月 + 两位日
- 单数月/日前加 `0`：`06-05`，不是 `6-5`

### 规则 3：版本号格式

- `v{n}`，n 从 1 开始递增
- 同日第一份不加版本号（版本号隐含为 v1）
- 版本号反映**产出顺序**，不是重要性：`v7` 比 `v5` 晚产出

### 规则 4：全小写 + 连字符

- 禁止：空格、下划线（`_`）、中文字符、大写字母（模板除外）
- 正确：`audit-2026-06-30.md`
- 错误：`Audit_2026_06_30.md`、`审计报告-2026-06-30.md`

### 规则 5：禁止主观褒义形容词（2026-09-13 细化）

**禁止**：`final` `definitive` `ultimate` `comprehensive` `complete` `professional`
`qualitative` `recursive`

理由（规则原意）：这些词是**自我评价**，读者无法核验，且会随时间失效。
**如果一份报告确实比前一份更完整——用版本号区分，让读者自己判断**。

**允许（范围标记白名单）**：`full`

区分标准：**该词描述的是「范围」还是「优劣」**。
`full` 在本仓的 `review-{date}-full[-v{n}].md` / `action-items-{date}-full.md` 中
标示**全仓评审**（对应局部评审，如 `action-items-{date}-bench.md`），是可核验的范围
描述，不表达"这份更好"。而 `comprehensive` 声称"全面"属自我评价。

> 2026-09-13 细化说明：此前 `full` 与褒义词同列于禁令，导致 6 份文件长期处于
> "违反规范"状态（见 §6.1）。核对规则原意后判定：它们违反的是规则的**文字**
> 而非**意图**，故细化规则而非改名——6 份文件已由本节接纳为合规范式。
> 新出现的范围标记词须先登记本白名单，不得自行取用。

## 四、类型定义

| 类型前缀 | 含义 | 何时产生 |
|---------|------|---------|
| `review-` | **评审报告**（现行主用）。对某变更集/全仓的评审，含发现清单与分级。 | 评审轮次产出时 |
| `audit-` | 对代码的审计报告。6 流逐行审计 + 10 维度评分 + 发现清单。 | `/audit` 命令执行后（**早期 corpus 用语，2026-06 至 07 使用**） |
| `audit-supplement-` | 审计补充报告。发现于审计后或针对特定维度的深度验证。 | 主审计报告后发现遗漏时 |
| `action-items-` | 可执行的任务清单。每项含优先级（危害×复杂度）+ 验证方式 + 涉及文件。 | 审计报告产出后，将发现转化为任务时 |
| `meta-audit-` | 对审计过程本身的审计。评估审计质量、识别误判、提炼改进方案。 | 审计轮次完成后 |

> **`review-` 与 `audit-` 的关系（2026-09-13 明确）**：二者都指「对代码的评审报告」，
> 区别只在 corpus 时期——`audit-` 是 2026-06/07 的用语，`review-` 是 2026-09 起的现行
> 用语（五轮全仓循环 `review-{date}-full-v{n}.md` 一致使用）。故 §七 原列的
> 「`review-` 是类型词错误（review≠audit）」**作废**：该判断出自 06 月，而 09 月的系列
> 已确立 `review-` 为事实标准且语义准确——这些文档确实是评审报告。
> **新文档一律用 `review-`；`audit-` 仅为历史 corpus 保留，不再新用。**

### 6.1 命名冲突处理结果（2026-09-13 已裁决并执行）

曾登记 7 份"违规"文件待裁决。按规则**原意**逐条核对后分为两类处置——
判据是「该词描述的是范围还是优劣」：

**A. 6 份由规则细化接纳（不改名）**

规则 5 原意是禁止**自我评价**（"如果一份报告确实比前一份更完整——用版本号区分"），
而 `full` 在这些文件名里标示**范围**（全仓轮次 vs 局部，如 `action-items-*-bench.md`），
可核验且不表达优劣；`review-` 则已由 §四 接纳为现行类型前缀。
故这 6 份违反的是规则的**文字**而非**意图** → 细化规则（规则 5 增范围标记白名单、
§四 增 `review-` 类型），而非改名：

| 文件 | 处置 |
|------|------|
| `action-items-2026-09-10-full.md` | 合规范式（`full` = 全仓轮，白名单接纳） |
| `review-2026-09-10-full.md` | 合规范式（`review-` 类型 + `full` 范围标记） |
| `review-2026-09-10-full-v2.md` | 同上 |
| `review-2026-09-11-full-v3.md` | 同上 |
| `review-2026-09-12-full-v4.md` | 同上 |
| `review-2026-09-13-full-v5.md` | 同上。另：该文件 2026-09-13 由 `review-2026-09-12-full-v5.md` **改名**——原文件名日期与其内容矛盾（标题与报告编号均为 2026-09-13，且 `action-items-2026-09-13-v5.md` 按内容日期引用它），同系列 v2/v3/v4 均满足「文件名日期 == 内容日期」，v5 是唯一破例，故错在文件名 |

**B. 1 份改名（真正违反规则意图）**

| 原文件 | 现文件 | 理由 |
|--------|--------|------|
| `comprehensive-review-2026-09-13.md` | `review-2026-09-13-architecture.md` | `comprehensive`（综合/全面）是**自我评价**，正是规则 5 要禁的；且类型词不在最前，违规则 1。内部评审编号 `REVIEW-COMPREHENSIVE-2026-09-13` 同步改为 `REVIEW-2026-09-13-ARCH` |

**存量已清零**：上述处理后无违规文件。新增文档一律遵守规范；范围标记词须先登记
规则 5 白名单，不得自行取用。改名如需追溯，用 `git log --follow <path>`。

## 七、时间视角规则（2026-09-13 新增）

**审计与清单文档的唯一时间视角是「当前代码库状态」，不是「本轮 vs 上轮」。**

### 规则 6：禁止会话相对表述

- **禁止**：`本轮` / `上轮` / `下一轮` / `本次会话` / `上两轮` / `下轮配额恢复后`
- **改用**：绝对日期 + commit 哈希 + 该轮的范围
- 理由（实证）：`action-items-2026-09-12-v4.md` 以「上轮 v3 已地毯」为由**缩减
  本轮扫描范围**，但该文档本身不含 v3 对应的 commit 与扫描范围，**读者无法独立
  验证这个范围决策是否成立**。审计结论若不可复现，审计即失效。

### 规则 7：版本号不承载会话语义

`v{n}` 只表示同日出产顺序（规则 3）。跨日轮次应在正文写明轮次日期与 commit，
不要依赖读者脑中的会话序列（`v3`/`v4`/`v5` 分属 09-10/09-11/09-12/09-13 四个日期，
仅看文件名无法还原先后与对应提交）。

### 写法对照

| ❌ 会话相对 | ✅ 绝对可查 |
|-----------|-----------|
| 「本轮结论：P1 全清」 | 「2026-09-10 轮（commit 043c9f1）结论：P1 全清」 |
| 「上轮 64 项修复中 4 项自带缺陷」 | 「2026-09-10 轮 64 项修复（commit 043c9f1）中 4 项有缺陷」 |
| 「下轮配额恢复后补全量地毯」 | 「待办：子代理配额 2026-09-17 恢复后补全量地毯（本文件 TODO）」 |

**存量**：`docs/` 下此类表述共 54 处（grep `本轮\|上轮\|下一轮\|本次会话` 计数），
集中在本目录的历史文档中。存量不追溯改写（成本高、收益低），**新产出遵守规则 6/7**；
做归档整理时按上表改写。
