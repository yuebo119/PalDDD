<details>
<summary><b>F-01 · EventLogPositionReserver catch(DbUpdateException) 过宽（ITM-065 同族第五处）</b></summary>

**证据**：`src/PalDDD.EventLog.EFCore/EventLogPositionReserver.cs:144-149`

```csharp
catch (DbUpdateConcurrencyException) { ... continue; }   // CAS 失败——正确窄化
catch (DbUpdateException) {                               // ← 过宽：任意 DbUpdateException
    // 主键冲突 —— 另一个进程先插入了分配器行。重试。
    context.Entry(allocator).State = EntityState.Detached;
    continue;
}
```

同族对照（均已窄化为 IsUniqueConstraintViolation 鸭子判定）：EventLogDbContext.cs、InboxDbContext.cs:179-224、IdempotencyDbContext.cs:177-221、ProjectionCheckpointDbContext.cs（ITM-003/ITM-065 修复链）——**唯独 EventLogPositionReserver 保留宽 catch**。连接断开、字段溢出、超时等其他 DbUpdateException 会被误判为"主键冲突"重试 5 次，最终抛出误导性的 "Failed to allocate a global position chunk after 5 optimistic concurrency retries"。

**定稿门三问**：①误判库对照 PD4（合规 catch 形态——此处无 when 过滤，非合规形态）；②反证搜索——查了同族 4 处均已窄化，无"故意宽 catch"的设计声明（XML 注释写的是"主键冲突"）；③触发路径——"调用 ReserveAsync 时 DB 连接中断/字段超长，则 5 次无效重试 + 误导性异常消息"。

**修复方案与验证方法**：复用 `EventLogDbContext.IsUniqueConstraintViolation` 同型鸭子判定（或提取共享工具），仅唯一约束冲突走 detach+continue，其余上抛。验证：构建 + 既有 800 测试全绿 + 新增负向测试（非唯一约束异常不再重试）。

</details>

<summary><b>F-02 · SagaStateDbContext.SaveChangesAsync 返回语义违背接口契约</b></summary>

**证据**：接口契约 `src/PalDDD.Transactions/ISagaStateStore.cs:34-36` 声明返回 "受影响行数：1 表示写入生效；0 表示目标行不存在或乐观锁冲突（他实例已写同一 Saga），调用方据此判定本实例内存快照作废"。EFCore 实现 `SagaStateDbContext.cs:105-106`：

```csharp
async ValueTask<int> ISagaStateStore<TState>.SaveChangesAsync(TState state, CancellationToken ct)
    => await SaveChangesAsync(ct);   // ← 返回 DbContext 实际写入的实体数
```

分叉场景：① 无变更保存 → EF 返回 0（非冲突）→ SagaProcessor.cs:165/184 按契约误判"乐观锁冲突"记 Warning 并丢弃快照；② 多实体一次保存 → 返回 N>1（契约只定义 0/1）。Dapper/PalORM/InMemory 三实现均返回受影响行数（0/1），唯 EFCore 返回实体计数。

**定稿门三问**：①PD17（跨实现分叉须枚举全部姊妹实现——已枚举 4 个）；②反证——接口注释 2026-08 曾"统一 EF/Dapper/内存三实现的返回值语义"，EFCore 显然未对齐；③触发路径——"SagaProcessor 对无实际变更的 Saga 状态调用 SaveChangesAsync → 收到 0 → 误记冲突 Warning + 快照作废"。

**修复方案与验证方法**：EFCore 实现改为检查目标实体在 ChangeTracker 中的状态：已写入返回 1、乐观锁冲突（DbUpdateConcurrencyException）返回 0；或包装为 `state` 的 Entry 判定。验证：构建 + 新增单元测试（无变更保存返回 1 或明确 0 语义、冲突路径 0）。

</details>

<summary><b>F-03 · Spec&lt;T&gt; 静态构造期无条件 Expression.Compile（Core 层 AOT 违约）</b></summary>

**证据**：`src/PalDDD.Core/ISpecification.cs:207-224`

```csharp
public static ISpecification<T> All { get; } = new ExpressionSpecification<T>(_ => true);  // 静态初始化即构造
...
internal sealed class ExpressionSpecification<T> : ISpecification<T>
{
    public ExpressionSpecification(Expression<Func<T, bool>> expression)
    {
        _expression = expression ?? throw ...;
        _compiled = _expression.Compile();   // ← 无条件编译（IL3050）
    }
}
```

`[UnconditionalSuppressMessage("AOT", "IL3050")]` 的 Justification 声称"AOT 场景应通过 ToExpression() 将表达式传递给 EF Core"——但 Compile 发生在**构造期**而非 IsSatisfiedBy 调用期，任何触碰 `Spec<T>.Where/All/None` 的代码在 NativeAOT 下构造即触发 `PlatformNotSupportedException`，抑制理由与实现不符。Core 层 IsAotCompatible=true（PDDD-G14 要求），此文件因含 "RequiresDynamicCode" 字样被 gate G8 豁免（gate-check.sh:304 按文件内字符串豁免）——**豁免被抑制消息文本误触发**。

**定稿门三问**：①PD3 不适用（Core 非适配器层，无 false 声明）；②反证——gate G8 豁免基于文件含 RequiresDynamicCode 字符串，但该字符串来自 SuppressMessage 文本而非 [RequiresDynamicCode] 标注，属豁免漏洞；③触发路径——"NativeAOT 发布的应用访问 Spec\<T\>.All → 构造期 Compile → PlatformNotSupportedException"。

**修复方案与验证方法**：Compile 延迟到首次 IsSatisfiedBy（lazy），ToExpression 路径零编译；或将该类型降级标注 [RequiresDynamicCode]。验证：构建 + AOT publish 探针（publish 后运行触碰 Spec\<T\> 的最小程序）。

</details>

<summary><b>F-06 · PalOrmSagaStateStore MySQL JOIN 租约跨 owner 覆盖竞态（待探针）</b></summary>

**证据**：`src/PalDDD.PalORM/Stores/PalOrmSagaStateStore.cs:84-87`：

```csharp
// MySQL 特化路径：JOIN 子查询
await Session.ExecuteAsync(
    $"UPDATE saga_states t JOIN (SELECT saga_id FROM saga_states WHERE status = ... AND (leased_until IS NULL OR leased_until <= {now}) ORDER BY created_at LIMIT {batchSize}) AS sub ON t.saga_id = sub.saga_id SET t.leased_by = {owner}, t.leased_until = {until}", ct);
```

REPEATABLE READ 下 derived table 按语句开始时的快照物化——两个不同 owner 的并发 UPDATE 都可能基于同一候选集；先到者提交后，后到者仍按其快照覆盖 `leased_by`，随后双方按 `(leased_by, leased_until)` 回读**同一批 Saga** → 双 worker 处理同批。现有注释仅声明"同一 owner 同 tick"场景，未覆盖跨 owner。Dapper 版（SagaLeaseActiveMySql）注释声明"由 SagaUpdate 的 version 乐观锁兜底"——PalORM 版缺同款兜底声明（其 SaveChanges 确有 version 乐观锁，但回读批次重复本身已造成双处理）。

**定稿门三问**：①PD22（MySQL 方言禁令家族）；②反证——version 乐观锁能防"重复保存"但防不了"双 worker 同时处理"（租约本身被覆盖）；③触发路径——"两个实例并发 LeaseActiveSagasAsync（不同 owner）→ 同一批 Saga 被两方回读处理"。⚠ 待探针：需 MySQL 双连接并发探针实证（dialect-probe 现为单 worker）。

**修复方案与验证方法**：先补双连接 MySQL 探针实证；修复方向——回读加 `status = Active AND leased_by = @owner` 二次过滤 + 乐观锁兜底，或文档化声明与 Dapper 对齐。验证：方言探针新增跨 owner 并发用例。

</details>
