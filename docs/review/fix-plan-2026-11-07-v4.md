## 2. 最终最优解（四项 + 关键约束，到代码形态）

### 2.1 B2：Rabbit 批量 pre-ack → `DeferredAckRegistry`（CWT + IVT）

**结构依据**（v3 §2.1 摘录有效，补充分支全貌）：`RabbitMqBroker.cs:479` 每次交付 `new RabbitMqMessageAck`；引用链 `broker:479 → handler 形参 :519 → 泵 lambda :94 → PumpItem.Ack :90 → batchAcks :243 → MessageBatchAck._inner`，**全链原样传递、无包装**（本轮新证），故 CWT 以该实例为 key 在两侧查到同一条目。

**唯一解**：

1. `PalDDD.Messaging` 新增 `internal static class DeferredAckRegistry`：`ConditionalWeakTable<object, Mark>`；`MarkDeferred(IMessageAck)` / `IsDeferred(IMessageAck)`。
2. `PalDDD.Messaging.csproj:17` 的 IVT 列表加 `<InternalsVisibleTo Include="PalDDD.Messaging.RabbitMQ" />`（RabbitMQ.csproj:13 已有 ProjectReference，无强命名）。
3. 标记落点**在四参生产者委托内、`channel.Writer.WriteAsync` 之前同步置位**（即 `EnqueueAsync` 的第一行，不放在 reader 侧 `Add`、也不放在 `PumpAsync`）。两个硬约束：① 顺序——编译探针 `CwtTiming.cs` 实证「先 WriteAsync 后打标记」在通道关闭时 `IsMarked=False`，broker catch 会兜底 Nack 与批次结算冲突；② 同步性——泵在 `MessageBatchPump.cs:101-103` 以 `Task.Run` 独立跑，标记若落在 reader 侧，broker 的 `await handler(...)` 返回后 :522 立即判定时标记尚未置位，pre-ACK 会间歇复发（红队 A-2）。
4. Rabbit broker 分支精确改判据（**含红队补入的 :522 与 :543/:555 悬空条件**）：

| 分支 | 行 | 消息是否进泵 | v4 判据 |
|------|----|------------|---------|
| deliveryCts ODE | :514 | 否（handler 未调用） | **保留无条件 Nack**；加判据也不生效，不得写成「跳过」 |
| 反序列化 null | :530 | 否 | **保留无条件 Nack**，同上 |
| 成功兜底 ACK | :522 | 是 | `!IsDeferred(ack) && !ack.IsSettled`（**B2 主缺陷就在此**，CWT 标记不会置 `IsSettled`，必须显式查 `IsDeferred`） |
| 关停 OCE | :543 | 是 | `if (!IsDeferred(ack) || !enqueueConfirmed) Nack`；关停时由泵补 `RejectAsync(false)` 兜底（见下） |
| 非关停 OCE | :555 | 是 | 同 :543 |
| 通用异常 | :564 | 是 | `!IsDeferred(ack) && !ack.IsSettled` |

   `:543`/`:555` 的 `enqueueConfirmed` 条件来自红队实证：`WriteAsync(deliveryCts.Token)` 在关停取消时可能抛 OCE、item 未入通道，而 `MessageBatchPump.cs:183-186` 的 `catch (OperationCanceledException) ... break` 关停时**不做** `batchAck.RejectAsync`，整批会悬空（重造 :547-553 注释所记「delivery 恒 unacked 占用 prefetch 名额」缺陷）。故 v4 追加：泵在 `catch (OperationCanceledException) when (ct.IsCancellationRequested)` 分支 break 前，对当前 `batchAck` 补一次 `RejectAsync(requeue:false, CancellationToken.None)`；broker 侧 :543/:555 才可在「已移交且入队已确认」时跳过 Nack。
5. Kafka 零影响：泵对任意 `IMessageAck` 都打标记，但 Kafka 侧兜底是 `HandleMessageAsync` 的 `finally`（`KafkaBroker.cs:837`），判据是 `ack is { IsSettled: false }`，**不查 `IsDeferred`** → 标记对 Kafka 无观察者，零行为变化（`KafkaBroker.cs` 不属于 Rabbit 的 IVT 消费方，也读不到 `IsDeferred`）。

**公共 API 影响**：零。`internal` 类型 + csproj 一行 IVT，不进快照、不改 CHANGELOG。红队 B 的两项待核已补：`Directory.Build.props` 全文零 `<AssemblyName>`/`<SignAssembly>`/`<PublicSign>` 覆盖；`ArchitectureBoundaryTests.cs` 无 IVT 白名单断言（仅 :930 有注释提及 InternalsVisibleTo 文本不可见）→ IVT 只需简单程序集名、无需 PublicKey，且不需同提交改边界测试。

**锁定测试**：批次 handler 成功前 delivery 恒 unacked（覆盖 :522 不提前 ACK）；批次收尾 AcknowledgeAsync 生效且零 Duplicate Warning；`RejectAsync(requeue:true)` 真重投；四参直接用户旧语义回归；`:514`/`:530` 两条「从未入队」路径仍 nack（不误跳过）；关停取消时 `WriteAsync` 抛 OCE 但标记已打 → 泵补 Reject 后无悬空、无二次 Nack；Kafka 批量订阅吞吐不退化。变异验证：删 `MarkDeferred` 调用 → unacked 断言转红；把标记移到 `WriteAsync` 之后 → 关停竞态用例转红；删泵关停分支的 Reject → 悬空用例转红。

### 2.2 B4：超时 abandoned scope → 分期，彻底修需改管道 ct 传递

**结构依据**：`TimeoutBehavior.cs:1-17` 文件头定案「超时只放弃等待，不中断 handler；框架不强制中断（进程内无法安全中止任意异步工作）」；`PipelineStateMachine.cs:25-85` 的 next 委托每管道只调一次、handler 用 `Reset` 捕获的 `_ct`；`Dispatcher.cs:310-312` 定案「HTTP 复用 RequestServices 以消除每请求两个 DbContext」；`ExceptionMiddleware.cs:106-128` 504 依赖 `await next` 抛异常。

**否决的形态（本轮实证，含红队 D 复核后修正）**：
- v3 的 Dispatcher `DrainAsync`：504 推迟 4.3×、重抛异常变 500、非 HTTP 路径未覆盖（F3/F4/F5）。
- linked CTS 中断 handler：违反 `TimeoutBehavior.cs` 文件头「框架不强制中断」定案。
- **红队 D 提出的「Dispatcher 自建 scope + 把 Dispose 挂到 `entry.Executor(...)` 返回 Task 的完成续体」：被代码证伪**。`TimeoutBehavior.cs:70-84` 的 `WaitWithTimeoutAsync` 在超时时 `throw CreateTimeoutException()`，`Executor` 返回的 Task 是**立刻 faulted 的短任务**，不包含仍在后台跑的 `running`；续体会在超时瞬间触发 → scope 提前释放，ODE 原样发生。要挂到真正的 `running`，仍需跨层任务引用（即 v3 的 AsyncLocal 袋），已由 F3/F4 否决。
- 全面改回自建 scope：违反 `Dispatcher.cs:310-312` 性能定案（每请求两个 DbContext 回归），须作为 ADR/性能裁决单列，不能静默做。
- 自建 scope + 延迟释放（`ScopeOwnership.cs` 探针）：算法上「504 立即写（119ms）+ scope 存活到 handler 完成」可行，但 handler 已用 `RequestServices` 解析完毕才触发超时，事后换 scope 结构上来不及。

**v4 分期（红队 C 复核后重写，不把 P1 降级成可观测糊弄）**：

- **B4 保持 P1，拆成两个独立条目**：① 根因修复（scope 生命周期）② 「CQRS 请求面无幂等键」双写项。两项都不得并入「已知缺口」一笔带过。
- **阶段 1（本轮，仅登记与披露，Warning 日志降为独立 P3 可观测项，不挂在 B4 名下充当交付）**：`usage.md:165` 补「504 后 RequestServices 已释放，abandoned handler 触碰 scoped 依赖抛 ODE」后果披露；`.ai/state.md` 未决项登记 B4-P1；`docs/decisions/` 落取舍记录（含复现判据与复评触发条件）；`ObserveFault` 补 Warning 作为**独立 P3 条目**单列（红队指出 `OnlyOnFaulted` 续体不改变运行时行为，也不让成功跑完的 abandoned 任务可见，不能充当 B4 修法）。**不改 504 时序、不改管道、不引入 AsyncLocal**。验收：504 端点集成测试锁死响应时刻 ≤ `_timeout + 50ms`；未决项三处（state/ADR/文档）grep 命中；Warning 用例单列。
- **阶段 2（需 ADR + 用户裁决，不在本方案实施）**：根因修复走「Dispatcher 侧 scope 归属」形态——改 `PipelineStateMachine` 让 `next` 接受可替换的 `IServiceProvider`，或引入请求级工作上下文承载 scope 生命周期；同时承担 `Dispatcher.cs:310-312` 性能定案回退的裁决。**红队 D 的定性批评成立**：我原先用 `TimeoutBehavior.cs` 文件头定案一并封死「scope 归属」形态是定性错误（文件头管的是「不中断 handler」，与 scope 生命周期正交）；v4 据此撤销该否决，把阶段 2 明确为 ADR + 性能裁决问题，而非「结构上不可能」。

> 与 v2 §1 J2 的关系：v2 批判「把数据完整性降级成可观测是错误定性」，v2 §7 又允许「504 时序无法在 scope 内等待时重新定性为已知未修缺口并登记，不许降级成计数器糊弄」。v4 按后者：保留 P1 定级、挂未决项、写 ADR 取舍、给复现判据与复评触发条件；Warning 日志不充当止血主体，文档披露只作附带动作。

**公共 API 影响**：零（阶段 1 只加日志与文档）。

### 2.3 S1：Rabbit 健康态 → 只做 channel 级故障置位

**结构依据**：`TryNackSafeAsync`/`TryAckSafeAsync`/`CancelConsumeSafeAsync`（`RabbitMqBroker.cs:654-679`、`:746-760`）的 catch 全是 `catch (Exception ex) when (ex is not OperationCanceledException)` 宽捕获，只记 Warning；**全仓零 `AlreadyClosedException` 类型引用**（本轮 grep 新证）。

**唯一解**：

1. `RabbitMqBroker` 追加 `, IMessageBrokerHealth`，加 `private volatile string? _consumeFaultReason`，实现两属性。
2. 置位判据**不给具体异常类型**（无现成依据）：改为在三个安全包装的 catch 里，用**消息内容启发式 + channel 状态**判定——`channel.IsOpen == false` 时置位（`IChannel.IsOpen` 是 RabbitMQ.Client 公开属性，需在实施轮用 `dotnet build` 探针核实 API 存在）。普通 handler 失败、普通 Nack 失败（channel 仍 open）**不置位**。
3. **删除 v3 的「Dispose 后置 Unhealthy」**：与 `HealthCheckExtensions.cs:166-170`「报 Degraded 会让默认应用 readiness 变红（滚动更新阻塞），语义变更风险高于收益，维持原判定」既有裁决冲突。
4. 同提交同步：公共 API 快照（2 个 property 行）、CHANGELOG、`HealthCheckExtensions.cs:169-170` 注释、`IMessageBrokerHealth.cs` remarks。

**公共 API 影响**：加法式契约变更（接口集合 + 2 个 public 属性），需快照 + CHANGELOG 同提交同步。

**锁定测试**：健康 broker → Healthy；`channel.IsOpen=false` 的 ack/nack 失败 → Unhealthy 且 `LastFaultReason` 非 null；毒消息 handler 失败但 channel 仍 open → 仍 Healthy；现有 `MessageBrokerHealthCheck_BrokerReportsUnhealthyConsuming_ReturnsUnhealthy` 保持绿。

### 2.4 S6：EF 终态写 → 三行拆分定级（入参卫生 P3 / 并发语义 P2 / Inbox 回退 P2）

**结构依据（本轮纠正）**：`InboxDbContext` 只有 **2 个** `Mark*`（:243 `MarkProcessedAsync`、:284 `MarkFailedAsync`）；`IdempotencyDbContext` 另有 2 个（:140/:158）。`InboxDbContext.cs:216,226` 显示本文件 `TryStartProcessingAsync` **已有** `affected==0` 处理，故「affected 门控」是既有模式，v3「EF 是唯一分叉」措辞不准，但「终态写缺回退」成立。

**定级（红队 E 复核后拆成两行，纠正我上一轮两度的过度判断）**：

| 子项 | 定级 | 依据 |
|------|------|------|
| Idempotency 入参假终态 | **P3 卫生，不做 `RestoreFromStore` + IVT** | 生产调用方只有 `IdempotencyProcessor.cs:116/:160`，`:181-184` 直接 `return IdempotencyExecution(Executed, result)`，`record` 是局部变量不跨调用留存。测试侧确有复用入参（`IdempotencyEfCoreTests.cs:129-142`、`DapperIdempotencyStoreTests.cs:175/:186`、`IdempotencyCrossStackMatrixTests.cs:71`），但断言走独立 reader / DB 真值（`IdempotencyEfCoreTests.cs:145-154` 用新 DbContext 读 `loaded`），**不读改后入参终态**。精确表述是「无生产消费者；测试侧复用存在但断言不读取入参终态」，不是「无消费者」 |
