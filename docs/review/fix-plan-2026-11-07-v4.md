## 2. 最终最优解（四项 + 关键约束，到代码形态）

### 2.1 B2：Rabbit 批量 pre-ack → `DeferredAckRegistry`（CWT + IVT）

**结构依据**（v3 §2.1 摘录有效，补充分支全貌）：`RabbitMqBroker.cs:479` 每次交付 `new RabbitMqMessageAck`；引用链 `broker:479 → handler 形参 :519 → 泵 lambda :94 → PumpItem.Ack :90 → batchAcks :243 → MessageBatchAck._inner`，**全链原样传递、无包装**（本轮新证），故 CWT 以该实例为 key 在两侧查到同一条目。

**唯一解**：

1. `PalDDD.Messaging` 新增 `internal static class DeferredAckRegistry`：`ConditionalWeakTable<object, Mark>`；`MarkDeferred(IMessageAck)` / `IsDeferred(IMessageAck)`。
2. `PalDDD.Messaging.csproj:17` 的 IVT 列表加 `<InternalsVisibleTo Include="PalDDD.Messaging.RabbitMQ" />`（RabbitMQ.csproj:13 已有 ProjectReference，无强命名）。
3. `MessageBatchPump.EnqueueAsync` 在 **`WriteAsync` 之前**调 `DeferredAckRegistry.MarkDeferred(ack)`。顺序是硬约束：编译探针 `CwtTiming.cs` 实证「先 WriteAsync 后打标记」在通道关闭时 `IsMarked=False`，broker catch 会兜底 Nack 与批次结算冲突；「先打标记」则 `IsMarked=True`、broker 跳过兜底。
4. Rabbit broker 分支精确改判据：

| 分支 | 行 | 消息是否进泵 | v4 判据 |
|------|----|------------|---------|
| deliveryCts ODE | :514 | 否（handler 未调用） | **保留无条件 Nack**（正确：消息从未入队） |
| 反序列化 null | :530 | 否 | **保留无条件 Nack** |
| 成功兜底 ACK | :522 | 是 | `!IsDeferred(ack) && !ack.IsSettled` |
| 关停 OCE | :543 | 是（泵 WriteAsync 抛 OCE 时已打标记） | `if (!IsDeferred(ack)) Nack` |
| 非关停 OCE | :555 | 是 | `if (!IsDeferred(ack)) Nack` |
| 通用异常 | :564 | 是 | `!IsDeferred(ack) && !ack.IsSettled` |

5. Kafka 零影响：Kafka 的 `KafkaMessageAck` 不进 CWT 注册表（泵只对包装路径打标记？——**不**，泵对任意 `IMessageAck` 都打标记，但 Kafka 侧的兜底是 `HandleMessageAsync` 的 `finally`（`KafkaBroker.cs:837`），判据是 `ack is { IsSettled: false }`，**不查 `IsDeferred`** → 标记对 Kafka 无观察者，零行为变化）。

**公共 API 影响**：零。`internal` 类型 + csproj 一行 IVT，不进快照、不改 CHANGELOG（与 v3 的 DIM 方案相反）。

**锁定测试**：批次 handler 成功前 delivery 恒 unacked；批次收尾 AcknowledgeAsync 生效且零 Duplicate Warning；`RejectAsync(requeue:true)` 真重投；四参直接用户旧语义回归；`:514`/`:530` 两条「从未入队」路径仍 nack（不误跳过）；关停取消时 `WriteAsync` 抛 OCE 但标记已打 → 无二次 Nack；Kafka 批量订阅吞吐不退化。变异验证：删 `MarkDeferred` 调用 → unacked 断言转红；把标记移到 `WriteAsync` 之后 → 关停竞态用例转红。

### 2.2 B4：超时 abandoned scope → 分期，彻底修需改管道 ct 传递

**结构依据**：`TimeoutBehavior.cs:1-17` 文件头定案「超时只放弃等待，不中断 handler；框架不强制中断（进程内无法安全中止任意异步工作）」；`PipelineStateMachine.cs:25-85` 的 next 委托每管道只调一次、handler 用 `Reset` 捕获的 `_ct`；`Dispatcher.cs:310-312` 定案「HTTP 复用 RequestServices 以消除每请求两个 DbContext」；`ExceptionMiddleware.cs:106-128` 504 依赖 `await next` 抛异常。

**否决的形态（本轮实证）**：
- v3 的 Dispatcher `DrainAsync`：504 推迟 4.3×、重抛异常变 500、非 HTTP 路径未覆盖（F3/F4/F5）。
- linked CTS 中断 handler：违反 `TimeoutBehavior.cs` 文件头既有定案；且 `PipelineStateMachine` 的 `_ct` 是 `Reset` 时捕获的，行为层拿不到可替换的 token。
- 全面改回自建 scope：违反 `Dispatcher.cs:310-312` 性能定案（每请求两个 DbContext 回归）。
- 自建 scope + 延迟释放：编译探针 `ScopeOwnership.cs` 证明「504 立即写（119ms）+ scope 存活到 handler 完成」在算法上可行，但**handler 已用 RequestServices 解析完毕才触发超时**，事后换 scope 结构上来不及。

**v4 分期（诚实定性，不把 P1 降级成可观测糊弄）**：

- **阶段 1（本轮，P1 可观测止血）**：`ObserveFault` 补 `IPalLogger.Warning`（记录 abandoned 任务故障、零日志缺陷闭合）；`usage.md:165` 补「504 后 RequestServices 已释放，abandoned handler 触碰 scoped 依赖抛 ODE」后果披露；`TimeoutBehavior` 备注与 ADR 登记「彻底修需改管道 ct/scope 传递」。**不改 504 时序、不改管道、不引入 AsyncLocal**。验收：504 端点集成测试锁死响应时刻 ≤ `_timeout + 50ms`；abandoned 异常有 Warning 可观测；文档 grep 命中。
- **阶段 2（需 ADR + 独立立项，不在本方案实施）**：改 `PipelineStateMachine` 让 `next` 接受可替换的 `CancellationToken`/`IServiceProvider`，或引入「请求级工作上下文」承载 scope 生命周期；届时才谈彻底修。**阶段 2 是设计决策，须用户裁决后另出 ADR，不允许在 v4 里静默实施**。

> 与 v2 §1 J2 的关系：v2 曾批判「把数据完整性降级成可观测是错误定性」。v4 阶段 1 明确标注为**止血**而非「修完」，阶段 2 保留 P1 定性并给出立项路径，避免重蹈该批判。双写风险（504 重试）属业务幂等键设计，继续登记为已知缺口。

**公共 API 影响**：零（阶段 1 只加日志与文档）。

### 2.3 S1：Rabbit 健康态 → 只做 channel 级故障置位

**结构依据**：`TryNackSafeAsync`/`TryAckSafeAsync`/`CancelConsumeSafeAsync`（`RabbitMqBroker.cs:654-679`、`:746-760`）的 catch 全是 `catch (Exception ex) when (ex is not OperationCanceledException)` 宽捕获，只记 Warning；**全仓零 `AlreadyClosedException` 类型引用**（本轮 grep 新证）。

**唯一解**：

1. `RabbitMqBroker` 追加 `, IMessageBrokerHealth`，加 `private volatile string? _consumeFaultReason`，实现两属性。
2. 置位判据**不给具体异常类型**（无现成依据）：改为在三个安全包装的 catch 里，用**消息内容启发式 + channel 状态**判定——`channel.IsOpen == false` 时置位（`IChannel.IsOpen` 是 RabbitMQ.Client 公开属性，需在实施轮用 `dotnet build` 探针核实 API 存在）。普通 handler 失败、普通 Nack 失败（channel 仍 open）**不置位**。
3. **删除 v3 的「Dispose 后置 Unhealthy」**：与 `HealthCheckExtensions.cs:166-170`「报 Degraded 会让默认应用 readiness 变红（滚动更新阻塞），语义变更风险高于收益，维持原判定」既有裁决冲突。
4. 同提交同步：公共 API 快照（2 个 property 行）、CHANGELOG、`HealthCheckExtensions.cs:169-170` 注释、`IMessageBrokerHealth.cs` remarks。

**公共 API 影响**：加法式契约变更（接口集合 + 2 个 public 属性），需快照 + CHANGELOG 同提交同步。

**锁定测试**：健康 broker → Healthy；`channel.IsOpen=false` 的 ack/nack 失败 → Unhealthy 且 `LastFaultReason` 非 null；毒消息 handler 失败但 channel 仍 open → 仍 Healthy；现有 `MessageBrokerHealthCheck_BrokerReportsUnhealthyConsuming_ReturnsUnhealthy` 保持绿。

### 2.4 S6：EF 终态写入参回退 → 两栈分形态（维持 P2）

**结构依据（本轮纠正）**：`InboxDbContext` 只有 **2 个** `Mark*`（:243 `MarkProcessedAsync`、:284 `MarkFailedAsync`）；`IdempotencyDbContext` 另有 2 个（:140/:158）。`InboxDbContext.cs:216,226` 显示本文件 `TryStartProcessingAsync` **已有** `affected==0` 处理，故「affected 门控」是既有模式，v3「EF 是唯一分叉」措辞不准，但「终态写缺回退」成立。

**维持 P2 的依据（推翻上一轮降级）**：`DapperIdempotencyStoreTests.cs:166-177` 的 `MarkCompletedAsync_StaleRevision_DoesNotMutate` 断言「并发抢占后入参仍 Processing」；`IdempotencyEfCoreTests` 全文件无同款用例。这是**跨栈契约在 EF 栈失守**，不是无消费者的理论缺陷。

**唯一解**：

- **Inbox（两方法）**：`MarkProcessedAsync`/`MarkFailedAsync` 变异前保存 `(Status, ProcessedAt, LastError)` 快照；`SaveTerminalStateAsync` 返回 `bool`（`affected > 0`）；非关系型 InMemory 分支的 `DbUpdateConcurrencyException` 同样回退。注意 C# 明确赋值：`affected` 在 `try/finally` 之后读取，需保证所有异常路径先赋值或改 `int affected = 0;` 初始化（实施轮用真实项目 `dotnet build` 三查验证，不靠玩具探针）。
- **Idempotency（两方法）**：并发冲突时不能简单回退 Processing（DB 已被另一节点写终态）。v3 的 `RestoreFromStore` + 新增 IVT 形态**保留**，但收窄为：仅 `DbUpdateConcurrencyException` 分支 `AsNoTracking` 重读 DB 行 → 调 `internal RestoreFromStore` 覆盖回入参（Status/Revision/ResponsePayload/Error/UpdatedAt，不递增 Revision）。给 `Idempotency.csproj` 加 IVT `PalDDD.Idempotency.EFCore`。
- 锁定测试对齐 Dapper 既有契约：EF 栈新增 `MarkCompletedAsync_StaleRevision_DoesNotMutate_EfCore`，与 `DapperIdempotencyStoreTests.cs:166` 同形态；Inbox 关系型 + InMemory 各一并发抢占用例（败者入参仍 Processing）。

**公共 API 影响**：零（新增 internal 成员 + IVT，`Mark*` 签名不变）。

### 7.3 自我纠正（推翻上一轮论证的一处结论）

上一轮论证 §三缺陷 10 判「S6 Idempotency 入参假终态无生产消费者 → 从 P2 降为 P3 卫生」。本轮全仓 grep 推翻该判断：`test/PalDDD.Integration.Tests/DapperIdempotencyStoreTests.cs:166-177` 的 `MarkCompletedAsync_StaleRevision_DoesNotMutate` **明确断言**「并发抢占（手动推进 revision）后入参 `record.Status` 仍为 `Processing`」；而 `IdempotencyEfCoreTests` 全文件无同款用例。这是**跨栈契约在 EF 栈失守**，不是无消费者的理论缺陷。

处置：v4 §1 裁决表第 10 行改判「维持 P2 修复」，§2.4 保留 `RestoreFromStore` + IVT 形态并要求 EF 栈补 `MarkCompletedAsync_StaleRevision_DoesNotMutate_EfCore` 同款锁定测试。该纠正已同步进 §2.4、§3 批 C、§6。
