# 幂等执行设计说明：为什么这样设计

> 面向首次接触 `PalDDD.Idempotency` 的开发者。本文只解释设计取舍的来由。
> API 用法见 [usage.md](usage.md) §使用 Command Idempotency，架构位置与持久化见 [architecture.md](architecture.md) §Idempotency。

## 一、问题从哪里来

重复请求不是异常情况，是分布式系统的常态：

- 用户双击提交按钮（按钮禁用之前请求已经发出）
- 客户端超时自动重试（移动网络抖动下尤其频繁）
- API 网关超时重放（网关没收到响应，不知道服务端是否已经处理）
- 浏览器刷新或后退重发 POST
- 运维手动重放失败请求

如果写接口没有幂等设计，以上任何一条都会变成重复下单、重复扣款、重复发券。关键认知是：这些重复**无法从服务端根除**（客户端超时与服务端提交之间没有共同时钟），所以目标不是"让请求只来一次"，而是"来多次也不把业务做坏，且重复请求拿到可控的结果"。

## 二、职责边界：与 Inbox 的分工

Pal.DDD 有两个防重复机制，处理不同来源的重复，不能互相替代（API 重试没有 MessageId，消息投递没有 HTTP 请求语义）：

| 机制 | 幂等键 | 防什么 |
|------|--------|--------|
| `IdempotencyProcessor` | `(OperationName, Key)` | HTTP/API 命令重试（客户端、网关、人工重放） |
| Inbox | `(ConsumerName, MessageId)` | broker 消息重复投递 |

## 三、设计取舍逐个解释

### 3.1 键为什么是二元组 `(OperationName, Key)`

单一 Key 要求调用方保证全局唯一，这在实际系统里很难做到（订单和支付的业务主键可能都是同一个数字）。加上操作名后，不同业务操作的 key 空间天然隔离，调用方只需在自己的操作内保持 key 唯一。

### 3.2 为什么需要"租约"

两个相同请求几乎同时到达时，只有一个应该执行 handler，另一个应该快速返回而不是排队等待。`TryStartAsync` 用一次原子写入抢占记录：赢家写入 `Processing` 状态并获得租约（`LockedUntil`），输家立即拿到 `null`，对应 `Skipped` 语义。

租约同时承担崩溃恢复：持锁进程崩溃后记录残留 `Processing`，租约到期后允许新请求抢占重放，不会永久阻塞。`ProcessingTimeout` 默认五分钟，按业务 handler 的最长执行时间配置。

### 3.3 为什么缓存结果 payload，而不是只记录"处理过"

重试的语义是"我要那次调用的结果"。只记录标记位的话，重复请求只能得到"已经处理过了"的通知，调用方还得自己再查一遍。缓存成功结果后，重复请求直接返回与首次相同的结果，调用方代码里没有"重试特殊路径"。

### 3.4 为什么 Failed 可以立即重试，Completed 却不可翻转

分界线是副作用是否已经发生：

- handler 抛异常时，副作用没有发生（或按未发生处理），记录标记 `Failed`，重试是安全的。
- handler 成功返回后，副作用已经发生。此时任何把 Completed 改回 Processing 的操作都会导致副作用重放。

所以状态机只允许向前走（`Processing → Completed / Failed`），`MarkCompletedAsync` 用 `Revision` 单调令牌做 CAS 保护。`Revision` 用 `long` 递增而不是时间戳，原因是时间戳受数据库列精度截断影响：两个 worker 在同一时刻回收同一个过期租约时，时间戳令牌可能双双命中，幂等保护被绕过；单调计数令牌在同样场景下必然冲突，只有一个能成功。

### 3.5 为什么序列化函数由调用方提供

框架不在内部绑定某种序列化方式。`ExecuteAsync` 的 `serializeResult` / `deserializeResult` 由调用方传入，源生成 JSON（AOT 项目）、MemoryPack、自定义编码都可以。框架如果用反射序列化，既破坏 AOT 边界，也剥夺调用方的编码选择。

### 3.6 为什么是命令层 API 而不是 HTTP 中间件

中间件看似"一处接入全局生效"，但有明确的适用边界：捕获响应体、处理异常回滚、与业务事务对齐，每一件都比"读一个请求头"复杂。把幂等判断放在命令层（handler 外面包一层 `ExecuteAsync`），语义更清楚：重复创建订单就返回同一个订单号，而不是原样重放 HTTP 响应。另外 Pal.DDD 是库而不是 HTTP 框架，命令层是它唯一能保证存在的位置。

### 3.7 为什么记录会过期（Retention）

"多久之内的重试算同一个请求"是业务问题，不是技术问题。支付确认可能 24 小时内重试都要去重，订单创建可能要保留 7 天。`IdempotencyPolicy.Retention` 就是这个窗口。过期记录不再参与幂等判定（`GetAsync` 视同不存在），同一 key 可以重新执行，这就是"过期记录可回收重建"的含义：Retention 也是可重新执行窗口。

跨字段不变式：`Retention` 必须大于等于 `ProcessingTimeout`（`Validate()` 强制），否则记录会在处理租约仍有效时过期，去重窗口失效。

### 3.8 为什么物理清理由应用侧负责

框架只保证逻辑过期，不启动后台清理任务。原因：清理频率、批量大小、执行时段（低峰窗口）是部署环境的事，库无法替应用决定；隐式后台任务还会与应用的迁移、备份、故障演练产生时序耦合。应用侧按 `ExpiresAt` 索引（适配器已建）定期批量删除过期行即可。

## 四、三态语义与调用方职责

`ExecuteAsync` 返回 `IdempotencyExecutionStatus`，三种状态对应三种调用方处理：

| 状态 | 含义 | 调用方应该做的 |
|------|------|----------------|
| `Executed` | 本次执行了 handler | 正常返回结果 |
| `Cached` | 命中已完成记录，返回缓存结果 | 正常返回结果（与首次相同） |
| `Skipped` | 另一请求正在处理（租约未到期）或结果不可重放 | 让客户端稍后重试（如返回 202 Accepted） |

## 五、边界与已知取舍

- **不做请求体比对**：同一 `(OperationName, Key)` 的不同请求体被视为同一请求，命中 Completed 记录时返回既有结果。调用方必须保证键与请求语义一一对应（把业务主键编入 Key），否则第二个不同请求会拿到第一个请求的结果。
- **OCE 不标失败**：handler 抛 `OperationCanceledException` 时不标记 `Failed`（取消意味着"不知道执行到哪一步"，标 Failed 会让重试立即重放可能已完成的副作用），记录保持 `Processing` 直到租约到期。该路径不产生指标与日志，由调用方按取消语义观测。
- **毒载荷降级**：schema 漂移导致缓存 payload 无法反序列化时降级为 `Skipped` 而不是抛异常，让调用方按"无可重放结果"分支处理，避免该 key 在整个保留窗口内每次命中都抛。
